# 20. После Фазы 10: что делать дальше

`docs/01-roadmap.md` — про путь «от нуля до работающего sandbox» (Фазы 0–10). Этот документ —
про то, что идёт **после**. Новые блоки в `01-roadmap.md` не добавляем.

Источник — разбор пробелов проекта по двум осям (SRE и agent harness) и два круга критики плана.
Первая версия была на 20 «модулей» с контрактом `module.json`; она отвергнута как инфраструктура
ради инфраструктуры. Что осталось — ниже.

## Рекомендации по порядку

1. **Упражнения Фаз 1–9** (непомеченные `[ ]` в `01-roadmap.md`: удаление пода, OOMKilled, drift
   через `kubectl scale`, silence, `AuthorizationPolicy`, `pg_dump`…) можно делать **до, после или
   вперемешку** с блоками ниже — см. следующий раздел. Они учат больше, чем любой новый код.
   Это ваши упражнения; делаете вы.
2. **Дальше — блоки 1–7 по порядку**, где порядок указан (в агентной оси он реальный, см. ниже).
3. После 2–3 закрытых блоков **пересмотрите список**: реальность покажет, что из «обязательного»
   оказалось неважным.

## Единственное правило для новых вещей

**Выключено по умолчанию, smoke-тест зелёный.** Всё новое включается явным флагом или отдельным
release/namespace; с выключенным `./scripts/smoke-test.ps1` проходит как после Фазы 10. Никакого
фреймворка модулей (`module.json`, Enable/Disable/Reset) — не нужен и не планируется.
Прежние соглашения проекта остаются: values в `values.schema.json` и bump `Chart.yaml`, сетевые
правила с обеих сторон и порт 4143, Pod Security `restricted`, Helm владеет replicas и pod
template, новые registry — в pull-through кэш.

## Упражнения Фаз 0–9 в любом порядке

Чтобы упражнения можно было проходить на проекте с уже реализованными блоками 1–7 и в любой
последовательности, зафиксировано четыре вещи:

1. **Поведение по умолчанию — как после Фазы 10.** Всё, что меняет то, что описано в phase-доках,
   выключено по умолчанию: structured output (`Llm:StructuredOutput=false`), трейсинг
   (`tracing.enabled=false`), рекордер агента, «шумные» алерты (отдельный release, ставится вручную),
   нагрузка `loadgen` ~5 rps, квоты и PDB. Включаете сами, на время блока; смоук-тест зелёный
   и с ними.
2. **Откат одной командой** — `scripts/reset-exercise.ps1`: `Apps` (по умолчанию, ~2–3 мин, данные
   сохраняются), `Platform` (плюс платформенный слой), `Cluster -Yes` (с нуля, ~9 мин, данные
   теряются). Он стартует остановленные ноды, снимает остатки упражнений (kill switch, эксперименты
   Chaos Mesh, `AuthorizationPolicy`), чинит mesh, возвращает релизы из values-файлов (в том числе
   после drift через `kubectl scale`) и запускает смоук-тест. Ваши правки в git он **не** откатывает,
   а только предупреждает.
3. **В каждом phase-доке (09–18) перед упражнениями** — блок «Предусловия и откат» с командой,
   подходящей именно этой фазе.
4. **Тег `phase-10-baseline`** — точное состояние кода и доков до реализации плана:
   `git switch --detach phase-10-baseline` (вернуться — `git switch master`).
   Если цифры в phase-доке не сходятся с тем, что видите, сверьтесь с этим состоянием.

Что откат не возвращает: данные Postgres (нужен `Cluster`), Silence в Alertmanager (завершить в UI),
файлы в `.local/` (результаты baseline и evals лежат на хосте и переживают `cluster-down`, а отчёты
агента на его PVC — нет). Единственное, что остаётся «испорченным знанием»: если вы уже делали
backup drill (блок 6), п. 6 из [13](13-phase-4-storage.md) пройдёт без сюрприза — чтобы получить его,
делайте упражнение до блока 6.

## Блок 1. Recorder + baseline

**Первая строка — это код.** Нужен выключаемый рекордер над `GuardedTool` (≈1 час): пишет JSONL
`(run, iteration, tool, args, result)` в `.local/`. Без него первый baseline нельзя проиграть, а
повторять 3×5 прогонов на 9B дорого. Сначала рекордер, потом прогоны.

**Baseline:** ≥3 прогона на каждый сценарий из `infra/chaos/scenarios.json` (5 сценариев),
одинаковые условия (модель, `-QuietMinutes`, версия образа). 9B недетерминирована (в
[18](18-phase-9-chaos-engineering.md): 0/3 → 2/3 на одном сценарии), поэтому результат —
**распределение** (медиана и разброс), а не точка.
Что сохраняем: score, токены, wall-time, какие tools и сколько раз вызваны. Без cost «улучшили»
может означать «точнее, но втрое дороже».

**Версия harness** для сравнения = git sha + хеш промпта + хеш описаний tools.
**Готово, когда:** есть `.local/evals/<версия>/` с распределением по каждому сценарию.
**Если упрётся** в контекст LM Studio или память машины — это результат; записать в `19` («что бы
сделал иначе»).

## Блок 2. Replay

Проигрыватель берёт записанные tool-ответы и прогоняет новый harness без кластера и без
изменения входных данных; сравниваются отчёты.

**Назначение — только парсинг, промпт, guardrails.** Он убирает вариативность кластера, но не
модели: 9B на тех же ответах всё равно ответит по-разному, поэтому и при replay нужны N прогонов.
Для выбора tools replay не годится: модель может позвать tool, которого в записи нет.

## Блок 3. Судья

- Рубрика — 3–5 **булевых** полей в JSON, не свободный текст (например: назвал причину;
  действие обосновано или его не было; уверенность разумна).
- **Сначала судья — вы.** Разметьте вручную 10–15 отчётов по рубрике. Это и калибровка, и проверка
  самой рубрики: если разметка занимает больше часа или вы сами не можете ответить однозначно —
  рубрика плохая, а не отчёты. Разбор расхождений — отдельная половина работы.
- Автоматический судья (другая, более сильная модель, не та 9B, которая пишет отчёты: иначе она
  согласна с любым текстом) — только если ручная разметка станет узким местом, например при
  сравнении 4 версий harness. Тогда сверять с вашей разметкой; согласие < 80 % — рубрика плохая.
- Регулярки game day остаются как дешёвый нулевой слой. Считать доверительные интервалы, а не
  одно число.

## Блок 4. Structured output

`response_format: json_schema` для Analyze (схема из C#-типа). Сначала проверить, что LM Studio с
выбранной моделью реально соблюдает схему; если нет — зафиксировать результат и оставить флаг
`Llm:StructuredOutput=false`. Прогнать тот же baseline и сравнить. Если `Parsed=false` исчез —
победа; если нет — дело было не в парсинге. Защитную проверку в коде оставить.

## Блок 5. Процессы SRE

Один вечер, без инфраструктуры:
- **Error budget policy** — одна страница в `docs/policies/`: пороги burn rate из ваших реальных
  алертов → действия (заморозка не-критичных изменений, приоритет надёжности, кто решает, как
  выходим). Политику пишете вы; заготовку с вашими числами могу сделать я.
- **Blameless postmortem** одного chaos-сценария руками, **не глядя в отчёт агента** (хронология,
  impact, триггер / причина / условия, action items). Потом сравнить с отчётом агента: что он видит
  и чего не видит.
- **Alert hygiene:** добавить 3–4 шумных алерта («CPU > 80 %», «p99 > 1 с» без SLO), понаблюдать
  сутки, обосновать, какие убрать, перевести в warning или оставить. Дедупликация агента
  (`AlertSuppressionMinutes`) — отдельный слой и тюнинг не заменяет.
- **Toil-рефлексия (30 минут):** по каждому скрипту — как часто запускаете и сколько заняло бы
  руками. Часть окажется ненужной.

## Блок 6. Backup drill + tracing

- **Backup drill:** `pg_dump` → удалить PVC → восстановить → замерить **RTO** (время до
  работающего сервиса) и **RPO** (потерянные записи). Разрушающий: делает свежий дамп заранее,
  требует подтверждения. Права агента не расширяются.
- **Tracing:** Tempo + OpenTelemetry в сервисах и в агенте (один backend, два источника).
  Включение флагом (`tracing.enabled`, по умолчанию off; в NetworkPolicy правило к Tempo только
  когда включено). Агент: run = trace, итерация = span, tool/LLM call = span (атрибуты: номер
  итерации, tool, размер результата, токены, задержка). Готово, когда на сценарии «задержка БД»
  виден конкретный медленный спан.

## Блок 7. Capacity (можно срезать)

`loadgen` принимает rps из values; ступенчатая нагрузка 5 → 200 rps, найти «колено», где p99
уходит за SLO. Расчёт реплик и стоимости в облаке **на бумаге, поверх измеренного**, не вместо
него. kind делит CPU хоста: колено покажет и ограничения вашей машины — это тоже вывод.

## Опциональные упражнения (каждое ≤ 1 вечера)

- **Canary** через Linkerd traffic split (веса `HTTPRoute`), ручной: 5 % → смотрим 10 минут. Без
  Argo Rollouts; это упражнение на шаг, не на автоматический гейт.
- **Resource governance:** Quota + LimitRange + PDB + `kubectl drain` ноды. Квоту в `sandbox`
  после упражнения снять.
- **Память между прогонами:** SQLite + FTS5 по прошлым отчётам, tool `find_similar_incidents`.
  Намеренно последняя: корпус крошечный, ценность отложенная. Результат — подсказка, а не истина.
- **MCP** — только если нужно переиспользовать tools вне проекта.

## Сознательно не делаем

Фреймворк модулей; parallel tool calls как фазу; MCP в основных маршрутах; отдельные фазы под
cost, tool-selection, alert hygiene и toil (это метрики и упражнения внутри блоков); Argo Rollouts;
vector store для памяти; on-call и paging; managed cloud; больше сервисов, типов chaos и слоёв
guardrails. Не трогаем то, что работает: failure handling, guardrails в глубину,
`Llm:AllowedModels`.
