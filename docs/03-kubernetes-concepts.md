# 03. Концепции Kubernetes — что и зачем

Для каждого объекта: **что это**, **какую проблему решает**, **как используем в проекте**,
**на что посмотреть руками**. Читать по мере прохождения фаз роадмапа.

## Как вообще работает Kubernetes (за 1 минуту)

Kubernetes — это система, которой вы описываете **желаемое состояние** («хочу 3 копии
сервиса X с такой-то конфигурацией»), а она постоянно приводит **фактическое состояние**
к желаемому. Этот механизм называется **reconcile loop** (цикл согласования):
контроллер смотрит на разницу «хочу vs есть» и делает шаг к «хочу». Запомните эту идею —
наш агент устроен похоже (см. [05](05-agent-architecture.md)).

Основные части кластера:
- **Control plane**: `kube-apiserver` (единственная дверь в кластер — всё, включая kubectl
  и нашего агента, ходит через него), `etcd` (база, где хранится желаемое состояние),
  `scheduler` (решает, на какую ноду поставить под), `controller-manager` (набор reconcile-циклов).
- **Worker nodes**: `kubelet` (запускает контейнеры на ноде), `kube-proxy` (сетевые правила для Services),
  container runtime (containerd).

---

## Pod
- **Что**: минимальная единица запуска — один или несколько контейнеров с общей сетью и томами.
- **Проблема**: контейнеры, которые должны жить вместе (приложение + sidecar-прокси mesh).
- **В проекте**: напрямую поды не создаём — их создают Deployment/StatefulSet.
- **Руками**: `kubectl get pods -n sandbox -o wide`, `kubectl describe pod ...`, `kubectl logs ...`.

## Deployment (и ReplicaSet)
- **Что**: описывает «N одинаковых подов из такого-то шаблона» и управляет обновлениями.
- **Проблема**: под умер — кто его поднимет? Как выкатить новую версию без простоя?
  Deployment создаёт ReplicaSet, тот поддерживает число подов; при обновлении — rolling update.
- **В проекте**: frontend, orders-api, worker, агент.
- **Руками**: удалить под и посмотреть пересоздание; `kubectl rollout status/history/undo`.

## StatefulSet
- **Что**: как Deployment, но поды имеют стабильные имена (`postgres-0`) и свой собственный том.
- **Проблема**: БД нельзя просто «заменить на одинаковую копию» — у неё есть данные и идентичность.
- **В проекте**: PostgreSQL.

## Service
- **Что**: стабильный адрес (DNS-имя + виртуальный IP) для группы подов, выбранных по labels.
- **Проблема**: поды смертны, их IP меняются. Service даёт постоянное имя `orders-api.sandbox.svc.cluster.local`
  и балансирует нагрузку.
- **Типы**: `ClusterIP` (только внутри кластера — по умолчанию), `NodePort` (порт на каждой ноде),
  `LoadBalancer` (внешний балансировщик облака), `Headless` (без виртуального IP — для StatefulSet).
- **В проекте**: ClusterIP для всех сервисов; снаружи заходим только через Ingress.

## Ingress и Ingress Controller
- **Что**: Ingress — правила HTTP-маршрутизации (хост/путь → Service). Ingress Controller
  (ingress-nginx) — реальный прокси, который эти правила исполняет.
- **Проблема**: не заводить по LoadBalancer на каждый сервис; единая точка входа с TLS, маршрутизацией по хостам/путям.
- **В проекте**: `https://sandbox.local` → frontend. В kind пробрасываем порты 80/443 с хоста.
- **Важно**: объект Ingress без установленного контроллера ничего не делает. Это частая ловушка.
- **Дальше**: Gateway API — более новая замена Ingress; можно попробовать в фазе 10.

## ConfigMap
- **Что**: не-секретная конфигурация (ключ-значение или файлы).
- **Проблема**: не пересобирать образ ради смены настройки; один образ — разные окружения.
- **Подключение**: как переменные окружения или как файлы в томе. Нюанс: env не обновляются
  в работающем поде, файлы — обновляются (с задержкой), но приложение должно их перечитать.
- **В проекте**: настройки сервисов, «режимы неисправности», конфиг агента (allowlist действий).

## Secret
- **Что**: то же, что ConfigMap, но для чувствительных данных.
- **Важно понять**: по умолчанию Secret — это **base64, а не шифрование**. Защита обеспечивается
  RBAC (кто может читать), шифрованием etcd at rest и внешними хранилищами.
- **Как в проде**: Sealed Secrets, External Secrets Operator + Vault/облачный KMS, SOPS.
- **В проекте**: пароль БД, API-ключ LLM. Позже — попробовать Sealed Secrets, чтобы секреты можно было хранить в git.

## Probes (liveness / readiness / startup)
- **liveness**: «процесс жив?» — если нет, kubelet перезапускает контейнер.
- **readiness**: «готов принимать трафик?» — если нет, под убирается из Service (но не перезапускается).
- **startup**: даёт медленному приложению время стартовать, прежде чем включится liveness.
- **Ловушка**: liveness, проверяющий зависимость (БД), приводит к каскадным рестартам. Liveness — только про сам процесс.

## Resources: requests и limits
- **requests**: сколько CPU/памяти гарантировано — по этому scheduler выбирает ноду.
- **limits**: потолок. Превышение памяти → `OOMKilled`; превышение CPU → троттлинг (замедление).
- **В проекте**: обязательно для всех; режим «утечка памяти» будет демонстрировать OOMKilled.

## Persistent Volumes: PV, PVC, StorageClass
- **PV** (PersistentVolume): реальный кусок хранилища в кластере.
- **PVC** (PersistentVolumeClaim): заявка «мне нужно 1Gi с режимом доступа RWO».
- **StorageClass**: «тип хранилища» и как его создавать автоматически (dynamic provisioning).
- **Проблема**: файловая система контейнера исчезает вместе с ним.
- **В kind**: StorageClass `standard` (local-path-provisioner) — данные лежат на диске ноды.
  В облаке на его месте был бы сетевой диск (EBS, Azure Disk).
- **В проекте**: PostgreSQL, хранилище Prometheus/Loki, отчёты агента.

## Namespace
- Логическое разделение кластера. Граница для RBAC, ResourceQuota, NetworkPolicy. Не граница безопасности сама по себе.

## RBAC: ServiceAccount, Role, RoleBinding
- **ServiceAccount** — «учётка» для пода. **Role** — что можно (verbs на resources в namespace).
  **RoleBinding** — кому выдать Role. ClusterRole/ClusterRoleBinding — то же на весь кластер.
- **В проекте**: ключевая защита агента — его ServiceAccount может читать почти всё, но
  менять только конкретные вещи в `sandbox`. Проверка: `kubectl auth can-i --as=system:serviceaccount:sre-agent:sre-agent ...`.

## NetworkPolicy
- **Что**: файрвол между подами по labels/namespace.
- **Проблема**: по умолчанию в k8s любой под может достучаться до любого.
- **Важно**: работает только если CNI поддерживает (в kind по умолчанию — kindnet, поддержка
  NetworkPolicy есть в новых версиях; иначе ставим Calico/Cilium).
- **В проекте**: default-deny в `sandbox`, явно разрешаем frontend→orders-api→postgres и scrape из monitoring.

## Helm
- **Chart** — пакет шаблонов манифестов. **Values** — параметры. **Release** — установленный экземпляр чарта.
- **Проблема**: десятки почти одинаковых YAML на каждый сервис и окружение; версионирование и откаты.
- **В проекте**: свой общий чарт `sandbox-service` для всех наших сервисов + готовые чарты
  сообщества для инфраструктуры (ingress-nginx, kube-prometheus-stack, loki, linkerd, chaos-mesh, postgresql).
- **Руками**: `helm template` (посмотреть, что получится), `helm diff` (плагин), `helm rollback`.

## TLS и mTLS
- **TLS**: клиент проверяет сервер по сертификату, трафик шифруется. Так работает HTTPS на Ingress.
- **mTLS** (mutual TLS): **обе** стороны предъявляют сертификаты. Сервер знает, *какой именно сервис*
  к нему пришёл — это основа zero-trust внутри кластера.
- **Проблема**: вручную выпускать, раздавать и ротировать сертификаты каждому сервису — ад. Это решает mesh.

## Service Mesh (Linkerd)
- **Что**: в каждый под добавляется sidecar-прокси; весь трафик сервиса идёт через него.
  Control plane раздаёт прокси сертификаты и конфигурацию.
- **Что даёт без изменения кода**: автоматический mTLS с ротацией сертификатов, метрики
  (success rate, latency) на каждое соединение, retries, timeouts, traffic split (canary).
- **Linkerd vs Istio**: Linkerd проще и легче — для обучения лучше начать с него. Istio мощнее
  (и сложнее); понять разницу — задача на фазу 6.
- **Цена**: дополнительная задержка и ресурсы на каждый под, ещё один компонент, который может сломаться.

## CRD и операторы
- **CRD** (Custom Resource Definition) — способ добавить в k8s свои типы объектов
  (`Certificate`, `ServiceMonitor`, `PodChaos`). **Оператор** — контроллер, который их обрабатывает.
- Почти всё «продовое» (cert-manager, prometheus-operator, Chaos Mesh) устроено именно так.
  Увидеть: `kubectl get crd`.
