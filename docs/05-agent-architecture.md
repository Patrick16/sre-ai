# 05. Архитектура агента: Ralph loop + RALF

Самая интересная часть проекта. Документ описывает, **как думать** о дизайне агента,
а не только что написать.

> Реализация (Фаза 7) — [16-phase-7-agent-mvp.md](16-phase-7-agent-mvp.md): Microsoft Agent Framework вместо «голого»
> HttpClient (раздел «LLM-клиент» ниже), completion check — «steady state namespace», один прогон на namespace.

## Что такое agent harness

LLM сама по себе умеет только одно: получить текст и вернуть текст. Всё остальное —
**harness** (обвязка), который пишем мы:

- решает, **когда** запускать агента (триггеры);
- собирает **контекст** и упаковывает его в промпт;
- даёт модели **tools** (функции, которые она может «вызвать») и реально их исполняет;
- крутит **цикл** «модель → вызов tool → результат → модель…» и решает, когда остановиться;
- **ограничивает** модель: что ей можно делать, сколько шагов, сколько денег/токенов;
- **записывает** всё, что произошло, и формирует результат.

Хороший harness делает так, что даже слабая/локальная модель ведёт себя предсказуемо,
а сильная не может натворить лишнего. Качество агента = качество модели × качество harness.

## Два цикла: Ralph loop снаружи, RALF внутри

Агент устроен как **два вложенных цикла**, у каждого своя задача:

| Цикл | Вопрос, на который отвечает | Кто решает, что делать дальше |
|---|---|---|
| **Ralph loop** (внешний) | «Задача решена? Если нет — пробуем ещё раз» | Детерминированный код (completion check) |
| **RALF** (одна итерация) | «Что происходит сейчас и какой следующий шаг?» | LLM предлагает, guardrails решают |

### Ralph loop — «крути, пока не решено»

Ralph loop — известный приём из мира coding-агентов: одну и ту же **задачу** подают агенту
снова и снова, пока не выполнен критерий готовности. Три ключевые идеи, которые мы берём:

1. **Каждая итерация начинается со свежего контекста LLM.** Не продолжаем бесконечный диалог,
   а начинаем заново. Зачем:
   - контекст не разбухает (критично для локальных моделей с маленьким окном);
   - модель не «залипает» на своей прошлой ошибочной гипотезе;
   - система за время итерации изменилась — правильнее посмотреть на неё заново, чем верить старым наблюдениям.
2. **Память живёт вне модели — в файле прогресса (`RunState`).** Между итерациями сохраняется
   только сжатая выжимка: какие гипотезы проверены и отброшены, какие действия сделаны и с каким эффектом,
   что осталось непонятным. Следующая итерация читает её первой. Так агент не повторяет то, что уже не помогло.
3. **«Готово» определяет код, а не модель.** LLM склонны рано объявлять успех. Критерий готовности —
   детерминированная проверка: «алерт resolved **и** SLI в норме N минут подряд». Модель может
   *считать*, что всё починено, но цикл остановится, только когда это подтвердят метрики.

Для SRE-агента «задача» звучит так: **«верни систему в steady state»**. Её формулирует
триггер (алерт или плановая проверка), и она не меняется между итерациями.

### RALF — что происходит внутри одной итерации

```
 Trigger (webhook Alertmanager | таймер | вручную)
    │
    ▼
 TaskSpec: цель + критерий готовности + лимиты         RunState (файл прогресса)
    │                                                   ▲            │
    ▼                                                   │            │
 ┌─────────────── Ralph loop (итерация i) ──────────────┼────────────┼───┐
 │  свежий контекст LLM = TaskSpec + RunState ◄─────────┼────────────┘   │
 │                                                      │                │
 │  R — Retrieve  детерминированно собрать: алерт, поды, события,        │
 │                ключевые метрики, свежие ошибки в логах                │
 │  A — Analyze   LLM рассуждает, при необходимости вызывает read-only   │
 │                tools (внутренний ReAct, ≤ MaxSteps) → Findings,       │
 │                гипотеза причины, (опционально) ActionProposal         │
 │  L — Lead      ActionProposal → Guardrails → dry-run | approve | auto │
 │  F — Feedback  подождать T, проверить эффект (improved / unchanged /  │
 │                degraded), записать audit, обновить RunState ──────────┘
 └───────────────────────────────┬──────────────────────────────────────┘
                                 ▼
                    Completion check (код, не LLM)
          ┌──────────────┬───────┴────────┬──────────────────────┐
          ▼              ▼                ▼                      ▼
     steady state    не решено,       нет прогресса /       исчерпаны лимиты
     → отчёт, стоп   лимиты есть      degraded              → эскалация, отчёт
                     → backoff,       → эскалация,
                       итерация i+1     отчёт
```

### Почему цикл разбит именно так

- **Retrieve отдельно от Analyze.** Базовый контекст собирается детерминированным кодом,
  а не LLM. Это дешевле, быстрее и надёжнее: модель сразу видит главное и не тратит шаги
  на очевидные запросы. LLM добирает детали через tools, только если нужно.
- **Lead отделён от Analyze.** Модель только **предлагает** действие в виде структурированных
  данных. Решение «выполнять или нет» принимает детерминированный код (guardrails).
  Модель физически не имеет tool «выполнить произвольную команду».
- **Feedback замыкает итерацию.** Без проверки эффекта агент — это скрипт «сделал и забыл».
  Сравнение «до/после» записывается в RunState и становится входом следующей итерации.
- **Ralph loop замыкает задачу.** Одна итерация может не справиться: первое действие помогло частично,
  или гипотеза оказалась неверной. Внешний цикл даёт агенту ещё попытку — уже с учётом того, что не сработало.
  Это та же идея, что **reconcile loop** в контроллерах Kubernetes: снова и снова сравнивать «хочу» и «есть».

### Опасности Ralph loop и защита от них

Цикл «пока не решено» без ограничений — это способ бесконечно перезапускать поды.
Поэтому у внешнего цикла жёсткие рамки:

| Риск | Защита |
|---|---|
| Бесконечный цикл | `MaxIterations` (например, 5) и `MaxWallTime` (например, 30 мин) |
| Повтор одного и того же действия | RunState хранит сделанные действия; повтор того же действия с эффектом `unchanged` запрещён policy |
| Агент делает хуже | Эффект `degraded` → немедленная остановка и эскалация, без новых действий |
| Нет прогресса | Две итерации подряд без новых фактов и без улучшения → эскалация |
| Система не успела отреагировать | Backoff между итерациями (k8s нужно время на rollout, метрикам — на окно `rate()`) |
| Шторм действий | Общий лимит действий на запуск и на кластер (см. [06](06-safe-actions-and-guardrails.md)) |

### Пример: как это выглядит на деле

Алерт `OrdersApiHighErrorRate`. Цель: error rate < 1% в течение 5 минут.

1. **Итерация 1.** Retrieve: 2 из 3 подов в `OOMKilled`. Analyze: гипотеза — утечка памяти.
   Lead: `restart deployment/orders-api` (auto). Feedback: error rate упал с 31% до 4% — `improved`, но цель не достигнута.
   RunState: «restart помог частично; память снова растёт».
2. **Итерация 2** (свежий контекст + RunState). Retrieve: память растёт линейно, рестарты продолжаются.
   Analyze: рестарт лечит симптом; в логах после последнего rollout — новая версия образа.
   Lead: `rollback deployment/orders-api` (approve — ждём человека). Feedback: после подтверждения error rate 0.3% — `improved`.
3. **Completion check:** error rate < 1% держится 5 минут → стоп. Отчёт описывает обе итерации.

### Как это ложится на код

```
RalphLoop.RunAsync(TaskSpec task)
  state = RunState.Load(task.Id)
  for i in 1..task.MaxIterations:
      iteration = new RalfIteration(freshLlmContext(task, state))
      result = await iteration.RunAsync()      // R → A → L → F
      state.Append(result)                     // сохраняется на диск после каждой итерации
      if completionCheck.IsDone(task) → return Finished(state)
      if result.Effect == Degraded or state.NoProgress → return Escalate(state)
      await backoff(i)
  return Escalate(state, "limits exhausted")
```

RunState сохраняется на диск после каждой итерации. Если агент упадёт или перезапустится,
он продолжит с того же места — та же идея устойчивости, что и у контроллеров k8s.

## Компоненты (проект `SreAgent.Core`)

| Компонент | Ответственность |
|---|---|
| `ITrigger` / `TriggerEvent` | Источник запуска: Alertmanager webhook, таймер, ручной |
| `TaskSpec` | Задача для Ralph loop: цель, критерий готовности, лимиты (`MaxIterations`, `MaxWallTime`, backoff) |
| `RalphLoop` | Внешний цикл: свежий контекст на каждую итерацию, completion check, остановка/эскалация |
| `RunState` | Файл прогресса между итерациями: проверенные гипотезы, действия и их эффект, открытые вопросы |
| `ICompletionCheck` | Детерминированная проверка «задача решена» по метрикам/алертам/статусам |
| `IObservationCollector` | Детерминированный сбор базового контекста (Retrieve) |
| `ContextBuilder` | Упаковка наблюдений в компактный промпт с бюджетом токенов |
| `ILlmClient` | Абстракция над моделью: сообщения, tools, tool calls, ответ |
| `ITool` / `ToolRegistry` | Описание tool (имя, JSON-схема параметров, read-only или action) и его исполнение |
| `RalfIteration` | Одна итерация R → A → L → F, внутренний ReAct-цикл с tools ограничен `MaxSteps` |
| `IGuardrail` / `ActionPolicy` | Проверка ActionProposal (см. [06](06-safe-actions-and-guardrails.md)) |
| `IActionExecutor` | Выполнение одобренного действия |
| `IVerifier` | Проверка эффекта действия (Feedback) |
| `IReportWriter` / `IAuditLog` | Отчёт и журнал (см. [08](08-reporting-and-audit.md)) |
| `AgentRun` | Полная история запуска (все итерации) — источник для отчёта; RunState — его сжатая выжимка для LLM |

Ключевой принцип: `Core` не зависит от Kubernetes и конкретной LLM. Тесты loop'а
пишутся на фейковых tools и «скриптованной» LLM, которая возвращает заранее заданные ответы.

## Tools

Tool для LLM — это функция с описанием и JSON-схемой параметров. Модель возвращает
«хочу вызвать `get_pod_logs` с `{pod: "orders-api-xyz", tail: 100}`», harness исполняет и
возвращает результат следующим сообщением.

**Read-only tools (фаза 7):**

| Tool | Что делает |
|---|---|
| `list_pods` | Поды namespace со статусом, рестартами, возрастом |
| `describe_workload` | Deployment/StatefulSet: реплики, образ, условия, история rollout |
| `get_events` | События k8s по объекту/namespace за период |
| `query_metrics` | PromQL instant/range (с ограничением на размер результата) |
| `query_logs` | LogQL с лимитом строк, по умолчанию только ошибки |
| `get_active_alerts` | Текущие алерты из Alertmanager |

**Action tools (фаза 8)** — не выполняют действие, а создают `ActionProposal`:
`propose_restart`, `propose_scale`, `propose_rollback`. Выполнение — только после guardrails.

**Правила хороших tools:**
- узкие и понятные модели (лучше `query_logs(app, level, since)`, чем «выполни LogQL»);
- результат **сжат** и ограничен по размеру — иначе локальная модель утонет;
- ошибки возвращаются модели текстом («pod not found»), а не роняют цикл;
- у каждого tool есть таймаут.

## LLM-клиент: OpenAI-совместимый API и LM Studio

LM Studio поднимает локальный сервер с тем же протоколом, что и OpenAI
(`POST /v1/chat/completions`), поэтому достаточно **одного** клиента с настраиваемыми
`BaseUrl`, `ApiKey`, `Model`:

```jsonc
// appsettings.json (пример)
"Llm": {
  "BaseUrl": "http://localhost:1234/v1",   // LM Studio; для облака — URL провайдера
  "ApiKey": "lm-studio",                    // для облака — из Secret
  "Model": "qwen2.5-14b-instruct",
  "Temperature": 0.1,
  "MaxSteps": 8,
  "MaxContextTokens": 16000
}
```

Варианты реализации: официальный пакет `OpenAI` для .NET или `Microsoft.Extensions.AI`
(общая абстракция `IChatClient`). Решение принимаем в фазе 7; учебно полезно сначала
написать минимальный клиент на `HttpClient`, чтобы увидеть сырой протокол tool calling.

**Нюансы локальных моделей:**
- не все поддерживают tool calling одинаково хорошо — выбирать модели с поддержкой
  function calling (Qwen 2.5/3, Llama 3.1+, Mistral и т.п.);
- маленькое окно контекста → ещё важнее сжатие данных в Retrieve;
- нужен **fallback-парсинг**: если модель вернула JSON в тексте вместо tool call — попробовать распарсить;
- ответы валидировать по схеме; невалидный ответ → одно повторное сообщение с ошибкой, затем стоп.

## Лимиты и остановка

Агент **обязан** останавливаться. Условия остановки итерации и всего запуска:
- модель вернула финальный ответ без tool calls;
- достигнут `MaxSteps` (вызовов tools внутри RALF-итерации) или `MaxIterations` (итераций Ralph loop);
- превышен бюджет токенов/времени;
- guardrails запретили действие и альтернатив нет → эскалация человеку;
- система вернулась в steady state (алерт resolved, метрики в норме).

## Состояние и память

- **Внутри итерации** — контекст LLM (сообщения и результаты tools). После итерации выбрасывается.
- **Между итерациями** — `RunState`: короткая выжимка, которую видит следующая итерация.
  Писать её — тоже работа harness: код фиксирует факты (действие, эффект), LLM в конце итерации
  добавляет 2–3 строки «что понял / что проверить дальше».
- **В рамках запуска** — `AgentRun`: полная история всех итераций. Всё сериализуется в отчёт.
- **Между запусками** (позже) — история инцидентов: «этот алерт уже был вчера, помог rollback».
  Начать с простых файлов/SQLite; векторный поиск — только если реально понадобится.
- **Runbooks**: Markdown-файлы с инструкциями «что делать при алерте X» — можно подкладывать
  в контекст по имени алерта. Это простейший и самый полезный вид «знаний» агента.

## Наблюдаемость самого агента

Агент — тоже сервис, и за ним тоже нужно следить: метрики (число запусков, шагов, вызовов
tools, токенов, длительность, предложенные/выполненные/отклонённые действия), структурные
логи каждого шага, дашборд в Grafana.

## Как будем развивать

1. Фаза 7: одна RALF-итерация без действий (Retrieve → Analyze → отчёт). Учимся получать полезный анализ.
   Затем — Ralph loop в режиме наблюдения: итерации повторяются, пока алерт не resolved (например, после
   ручного исправления или окончания хаос-эксперимента). Так отлаживаются RunState и completion check без риска.
2. Фаза 8: добавляем proposals, guardrails, dry-run, затем approve, затем auto для самых безопасных действий.
   Теперь Ralph loop реально «чинит, пока не починит» — в рамках лимитов.
3. Фаза 9: оцениваем агента на хаос-сценариях: правильно ли нашёл причину, правильное ли действие,
   сколько шагов/времени. Это по сути **evals** для агента — набор сценариев с ожидаемым результатом.
