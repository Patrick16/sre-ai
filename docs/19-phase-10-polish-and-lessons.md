# 19. Фаза 10: всё с нуля одной командой и итоги проекта

## Одна команда

```powershell
./scripts/up.ps1          # пустой Docker → проверенный, работающий sandbox
./scripts/smoke-test.ps1  # «всё ли работает?» — в любой момент, только чтение
```

[up.ps1](../scripts/up.ps1) — это не новый деплой, а порядок уже знакомых шагов плюс проверка результата:

```
prerequisites   версии docker / kind / kubectl / helm 4 / dotnet, Docker запущен
cluster-up      kind (3 ноды, 80/443 только на 127.0.0.1) + pull-through кэши образов (переживают cluster-down)
deploy-infra    namespaces, политики, мониторинг → Traefik → cert-manager + CA → Linkerd → Loki/Alloy → Chaos Mesh → дашборды
build-images    4 образа .NET, теги из values-файлов релизов, kind load
deploy-apps     секреты (генерируются один раз) → postgres → orders-api → worker → frontend → loadgen → sre-agent
smoke-test      24 проверки
```

Скрипт идемпотентен: на живом кластере он заново применяет всё и ничего не ломает — это свойство Helm
(`upgrade --install`) и `kubectl apply`, а не отдельная логика.

**Почему smoke test, а не «скрипты отработали без ошибок».** В Фазе 9 после перезапуска Docker Desktop все скрипты
были довольны, а сайт отвечал 500: поды запустились вне mesh. [smoke-test.ps1](../scripts/smoke-test.ps1) проверяет
то, что видит пользователь и что нужно агенту:

- ноды и поды готовы во всех 10 namespace; **каждый** под в `sandbox`/`sre-agent` — с `linkerd-proxy`;
- сайт и API через Ingress по HTTPS (frontend → orders-api → postgres — вся цепочка);
- Grafana, Alertmanager; цели Prometheus в `sandbox` — `up`; SLI-правила считаются; логи доходят до Loki;
- admission policies агента на месте; агент готов и в режиме `DryRun` (а не оставлен в Auto после game day);
- LM Studio с моделью — предупреждение, не ошибка: без модели агент не думает, но кластер в порядке.

### Подъём с нуля: что показала проверка

`cluster-down` → `up.ps1` на прогретых кэшах образов — **с первого раза, 8 мин 32 с**, smoke test 24/24:

| Шаг | Время |
|---|---|
| prerequisites | 0:01 |
| кластер kind + кэши | 0:39 |
| платформа (мониторинг, Traefik, cert-manager, Linkerd, Loki, Alloy, Chaos Mesh) | 5:07 |
| 4 образа .NET + kind load | 0:53 |
| 6 Helm-релизов приложений | 0:40 |
| smoke test (включая 60 с на первые scrape) | 1:10 |

Платформа — 60% времени: каждый чарт ставится с `--wait`, а Linkerd и Prometheus стартуют дольше всех. Без кэшей
образов (первый запуск на новой машине) добавьте 10–20 минут на загрузку. Предупреждения `would violate PodSecurity
"baseline"` при подъёме — ожидаемые: это `warn`-метка привилегированных namespace (node-exporter, Alloy,
chaos-daemon), которые по своей сути читают хост.

Smoke test не проверяет, **думает** ли агент. Поэтому после подъёма — ручной health check (`POST /runs {}`) на свежем
кластере: `Resolved` за одну итерацию, 256 с, 3 вызова tools, ~8.5k токенов. Вывод — «временные сбои readiness
(502) у подов frontend при старте, восстановились сами», действий не предложено — ровно то, что произошло: frontend
поднимался раньше, чем orders-api стал готов. Путь агент → LM Studio через default-deny egress работает с нуля.

## GitOps (Argo CD): описание, без внедрения

Сейчас деплой — **push**: человек запускает `deploy-apps.ps1`, Helm применяет. GitOps — **pull**: в кластере живёт
контроллер (Argo CD, Flux), который постоянно сравнивает кластер с git и приводит его к git. Тот же reconcile loop,
что у Deployment-контроллера и у Ralph loop агента — только «желаемое состояние» лежит в репозитории.

Как бы это легло на проект:

| Сейчас | С Argo CD |
|---|---|
| `deploy-apps.ps1` → `helm upgrade` по каждому values-файлу | `Application` на каждый релиз: `source.path: infra/helm/sandbox-service`, `helm.valueFiles: [../releases/sandbox/orders-api.yaml]` — или одно `ApplicationSet` с генератором по папкам `releases/*/*` |
| порядок postgres → orders-api → … в скрипте | `argocd.argoproj.io/sync-wave` в Application (postgres — волна 0, клиенты — 1, агент — 2) |
| «не делай `kubectl edit`, будет конфликт с Helm» | Argo видит дрейф и (с `selfHeal: true`) возвращает git-версию — правило становится механизмом |
| секреты генерирует скрипт | секретов в git быть не может: External Secrets Operator / Sealed Secrets / SOPS |
| образы `kind load` с тегом из values | Argo не собирает образы: нужен реестр (локальный `registry:2` на сети `kind` уже есть — кэши) и CI, который пушит образ и меняет тег в values коммитом |

Где GitOps **столкнётся** с тем, что построено:

- **Действия агента.** `restart_deployment` пишет аннотацию `restartedAt`, которой нет в git. Argo с server-side diff
  игнорирует поля чужих field managers, но с client-side diff увидит дрейф и при `selfHeal` откатит — нужен
  `ignoreDifferences` на эту аннотацию. Та же история, что с Helm в Фазе 8: у каждого поля должен быть один владелец.
- **Chaos-режимы.** `helm upgrade --set-json faults.errorRatio=0.3` — это дрейф от git, и `selfHeal` его «починит»
  через минуту. В GitOps сбой включают **коммитом** (и выключают revert'ом) — эксперимент становится видимым в истории,
  что для game day даже лучше. Chaos Mesh CRD — тоже Application, но с `prune: false`, чтобы `kubectl delete` для
  досрочной остановки не боролся с Argo.
- **Агент перестаёт быть единственным писателем.** «Чинить» начинают двое: Argo (к git) и агент (к steady state).
  Правильная граница: агент меняет только то, чего нет в git (рестарт), а всё, что в git (реплики, образ),
  предлагает как **pull request** — следующий логичный режим после `Approve`.

Почему не внедряли: GitOps — про процесс команды (ревью, история, откаты коммитом). В песочнице с одним человеком и
без реестра он добавил бы три компонента (Argo, реестр, CI) ради того же результата, что `up.ps1`.

## Итоги: что выучено

**Kubernetes**

- Всё в k8s — reconcile loop: объявляешь «хочу», контроллер бесконечно сравнивает с «есть». Deployment, ReplicaSet,
  cert-manager, Linkerd identity, Helm 4, Argo CD, Ralph loop агента — одна и та же идея. Поняв её один раз,
  понимаешь большинство компонентов.
- **У каждого поля один владелец.** Server-side apply сделал это явным: `managedFields`, конфликты Helm с `kubectl
  scale`, аннотация рестарта агента, будущий GitOps. Самая частая причина «почему он вернул обратно».
- Probes — это политика, а не проверка здоровья: readiness, которая смотрит на базу, превращает падение базы в
  падение всех реплик (Фаза 4).
- Безопасность — слоями, не доверяющими друг другу: Pod Security, NetworkPolicy default-deny, mTLS с identity на
  ServiceAccount, RBAC, admission policy. RBAC не умеет «только эту аннотацию» — для этого есть CEL в API-сервере.
- Mesh — это порядок старта и порт 4143. Две самые дорогие ошибки фазы 6 и 9 — не в YAML, а в последовательности
  событий.

**SRE**

- Алертить на симптомы пользователя (SLI/burn rate), а не на причины (CPU): CPU stress дал 100% троттлинга и 0%
  влияния. Burn-rate алерты медленные **намеренно** — и из-за этого не годятся как критерий «починено».
- Хаос ценен опровергнутыми гипотезами. Подтверждённые — приятно, опровергнутая (CPU) — научила больше всех.
- Эксперимент требует гигиены: steady state до, тихий период, чистое состояние после. Иначе следующий эксперимент
  измеряет хвост предыдущего.

**Агент**

- **Harness важнее модели, данные важнее промпта.** Все крупные улучшения — не в формулировках: «scaled to ZERO» в
  данных tools (Фаза 7), факты отдельно от гипотез и синтез (Фаза 7), латентность и возраст событий в Retrieve
  (Фаза 9). От 0/3 к 2/3 — без единой правки системного промпта.
- **«Готово» решает код.** Модель охотно объявляет успех; completion check по метрикам — нет. Но и его пришлось
  уточнять трижды: алерты → алерты + SLI → + поды и рестарты.
- **Модель только предлагает.** Поле `action` в JSON, а не tool; guardrails в коде; RBAC и admission policy в
  кластере, которые не верят коду. За game day: 9 предложений рестарта, выполнен 1. Самый полезный guardrail
  (`current-symptom`) появился не из дизайна, а из e2e-прогона, где агент рестартовал здоровый сервис.
- **До/после ≠ причина.** «Improved» после рестарта может быть естественным восстановлением. Измерение — факт,
  причинность — нет; отчёт должен это различать.
- Модель на 9B: хорошо пересказывает явное, плохо выводит неявное и держится за самый «громкий» сигнал. Это
  ограничение, вокруг которого проектируется harness, а не баг, который чинится промптом.

## Что бы сделал иначе

1. **Smoke test с первой фазы**, а не с последней. Каждая фаза проверялась вручную, и холодный старт mesh нашёлся
   случайно, а не тестом.
2. **Оценку агента — раньше и строже.** Game day появился в Фазе 9, а мог бы в Фазе 7: сценарии + scorecard с первого
   дня агента дали бы цифры для каждого изменения harness. И сразу LLM-судья вместо регулярок, которые засчитали
   «лимит мал» за «утечку».
3. **Реестр образов вместо `kind load`.** Pull-through кэши уже были — ещё один `registry:2` для своих образов убрал бы
   «пересобрал тот же тег — сделай rollout restart» и открыл дорогу GitOps.
4. **Время у каждого сигнала с первого дня.** Половина ошибок агента — от данных без времени: старые логи, `lastState`
   без «когда», 5-минутные окна. Retrieve должен был изначально писать «X, N минут назад».
5. **Меньше фаз ради инфраструктуры, раньше — агент.** Mesh и mTLS полезны как урок, но агенту они дали в основном
   проблемы (4143, холодный старт). Агент MVP после наблюдаемости (Фаза 5) и mesh потом — порядок, при котором каждое
   новое усложнение сразу проверяется агентом.

## Код-ревью после Фазы 10 (2026-11-10)

Полный отчёт: [code-review-2026-11-10.md](code-review-2026-11-10.md); то же простыми словами —
[code-review-2026-11-10-simple.md](code-review-2026-11-10-simple.md). Все 20 пунктов исправлены. Урок: **самые
опасные ошибки были в обработке сбоев, а не в основном сценарии.** Каждый из них проявляется только когда что-то уже
сломано, поэтому game day их не нашёл:
- действие выполнено, а потом упала *проверка* — и действие исчезало из отчёта;
- *проверка завершения* упала — и прогон умирал, хотя остальной код специально «переживал» такие сбои;
- очередь клала запрос в канал раньше, чем записывала его в журнал (гонка), а `BoundedChannelFullMode.DropWrite`
  возвращает `true` даже когда выбрасывает запись — «очередь полна» не обнаруживалась;
- защита «ровно два действия» проверяла не все поля Deployment (`paused`, labels, finalizers).
Правило: для каждой операции с побочным эффектом спрашивать «что, если упадёт сразу ПОСЛЕ неё?» и писать на это тест.

Принятые решения, оставшиеся как есть: базовые образы Docker (`sdk:10.0`, `aspnet:10.0`) не закреплены по digest —
для локальной песочницы без реестра это сознательный компромисс (закрепление без автоматического обновления быстро
устаревает); возобновление прерванного прогона не реализовано (RunState — журнал, см. docs/16).
