# 13. Phase 4: data storage — PV, PVC, StatefulSet, PostgreSQL

The theory — the sections "StatefulSet" and "Persistent Volumes" in [03-kubernetes-concepts.md](03-kubernetes-concepts.md).

## Why

In Phase 1 the orders lived in the pods' memory: each of the 3 replicas had its own list, and after a restart everything disappeared.
Now orders-api (0.2.x) stores orders in PostgreSQL, and the database itself keeps its data on a persistent volume.

## What is deployed

```
orders-api ×3 ──► Service postgres:5432 ──► postgres-0 ──► PVC data-postgres-0 ──► PV pvc-… ──► a folder on the disk of node sre-ai-worker
                  Service postgres-headless (clusterIP: None) → DNS postgres-0.postgres-headless.sandbox.svc.cluster.local
```

| Object | Where from | Why |
|---|---|---|
| StatefulSet `postgres` (1 replica) | [statefulset.yaml](../infra/helm/postgres/templates/statefulset.yaml) | A stable pod name `postgres-0` and its "own" volume, which survives the pod being recreated |
| `volumeClaimTemplates` → PVC `data-postgres-0` | the same file | The PVC is created on the first start and permanently bound to the pod's name |
| `persistentVolumeClaimRetentionPolicy: Retain` | the same file | The PVC is **not deleted** on `helm uninstall` or when the replica count is reduced |
| Headless Service + a regular Service | [services.yaml](../infra/helm/postgres/templates/services.yaml) | A stable DNS name of a specific pod / an address for clients |
| Secret `postgres-credentials` | generated by [deploy-apps.ps1](../scripts/deploy-apps.ps1) | The password is shared by the database and orders-api; **it is never regenerated**, otherwise the applications cannot log in to the already initialized database |

### Running PostgreSQL without root
The official image starts as root by default and then switches to the `postgres` user — Pod Security
`restricted` would not admit that. So: `runAsUser/runAsGroup/fsGroup: 999` (the uid of the `postgres` user in the image),
the root filesystem is read-only, and the writable places are separate volumes: a PVC at `/var/lib/postgresql`
(in PostgreSQL 18 the data lives in `/var/lib/postgresql/18/docker`), an `emptyDir` for `/var/run/postgresql` (the socket) and `/tmp`.

### What changed in orders-api
- Orders are the table `orders`; the field `storedOnPod` became `createdByPod` (now it means "which pod accepted the order", not "where it is stored").
- The schema is created **lazily**, on the first request, under `pg_advisory_xact_lock` — the three replicas start at the same time
  and would otherwise race on `CREATE TABLE`. In production, migrations are usually moved into a separate Job (for example, a Helm `pre-upgrade` hook).
- **Probes do not depend on the database.** If the database is down, the orders-api pods are not restarted and are not removed from the load balancing;
  they answer `503 database unavailable`. For people, dashboards and the agent there is a separate `/health/db`.

## What we found during verification

### 1. Shared state
Both frontend pods, through **different** orders-api pods, see the same 5 orders; the worker processed all of them (`processed: 5`).
The effect "each replica has its own list" from Phase 1 is gone.

### 2. Deleting the database pod — the data is in place, about 3.5 s of downtime
`kubectl delete pod postgres-0` under continuous requests to `/api/orders` (every 300 ms):
```
probe 200: 11   probe 503: 7      (503 from 36.4 to 39.9 s)
orders before: 5 → after: 5,  PVC uid the same
LOG:  database system was shut down at ...   ← a clean shutdown, no crash recovery
```
The StatefulSet recreated the pod with the **same name** on the **same node** and attached the **same** PVC. Clients received a tidy 503
the whole time, not a hang. PostgreSQL managed to shut down cleanly (SIGINT from the image's `STOPSIGNAL` →
a "fast shutdown"; `terminationGracePeriodSeconds: 60` gave it the time).

### 3. The data is simply a folder on one node
```
PV path = /var/local-path-provisioner/pvc-…_sandbox_data-postgres-0
nodeAffinity: kubernetes.io/hostname in [sre-ai-worker]
drwxrwxrwx root  .        ← the provisioner creates the directory with 0777
drwxr-xr-x 999   18/      ← from here on everything belongs to the postgres user (63 MB after initdb)
```
The PV's `nodeAffinity` is the main limitation of local storage: if the node `sre-ai-worker` dies, the database pod **cannot
move** to another node — its volume is physically there. That is why production uses network disks (EBS, Azure Disk,
Ceph) or replication at the database level itself (CloudNativePG, Patroni).

### 4. `helm uninstall` did not delete the data
The StatefulSet and the pod were deleted, the PVC remained (the `Retain` policy); `/api/orders` → 503. After reinstalling — all 5 orders.

### 5. Deleting the PVC — a real data loss
- While a pod uses the PVC, deletion "hangs": the finalizer `kubernetes.io/pvc-protection` keeps it in `Terminating`,
  and the data stays readable.
- After the pod is deleted, the StatefulSet creates a pod and a **new, empty** PVC; the old PV was deleted together with its folder
  (the StorageClass `standard` has `reclaimPolicy: Delete`).

### 6. A bug found: the health check is green, but the service is broken
The first version of orders-api (0.2.0) remembered "the schema is already created". After the database was swapped for an empty one:
```
/health/db: Healthy
/api/orders: 503 503 503 503 …    ← forever
log: Database unavailable: 42P01: relation "orders" does not exist
```
The database is alive, the health check is green, and the service does not work — and the error text even lies ("database unavailable").
Fixed in 0.2.1: on `UndefinedTable` the flag is reset, the schema is recreated, and the request is retried.
An excellent future scenario for the agent: "the checks are green, the users are suffering".

### 7. The first request after a database restart fails
Even with 0.2.1, the first request on each pod after a database restart returns 503:
`57P01: terminating connection due to administrator command`. The connections in the Npgsql pool "died" together with the server,
and the first use of each of them fails. Npgsql does not retry requests itself — that is done at the application level
(a retry for idempotent operations, for example with `Microsoft.Extensions.Resilience`). Exercise 8.

### 8. Found in the code review of 2026-11-10 (orders-api 0.5.0)
- **A client error looked like a database failure.** `POST /orders` without `item` or with `null` violated `NOT NULL`, and a
  `PostgresException` is an `NpgsqlException`, so the filter answered 503 "database unavailable": the SLO burned, and the agent
  looked for a non-existent database problem. Now: validation of the body (a non-empty `item`, up to 200 characters) → 400; database errors
  of classes 22/23 (bad data / a violated constraint) are also 400; 503 — only when the database is really unavailable.
- **The list "froze".** `GET /orders` returned the first 100 orders of all time (`ORDER BY created_at`), so the frontend page
  always showed the same thing. Now the common list shows the newest first (`DESC`); the worker's queue
  (`status=pending`) stayed by age — that is FIFO, and that is correct. An index on `created_at` was added.
- **The database grew without limit.** loadgen creates ≈1 order/s, and the PVC is only 1 GB: after weeks the disk would run out and PostgreSQL
  would stop accepting writes. Now `Orders__RetentionHours: "24"` — a background task deletes *processed* orders
  older than a day (unprocessed ones — only after 7 days, `Orders__PendingRetentionDays`: if the worker never came back, they would otherwise pile up forever). So in the data-safety exercises, orders older than a day
  will no longer be found — this is expected.

for the full experience, start from a clean `-Level Cluster`.

| # | Do | What to expect |
|---|---|---|
| 1 | `kubectl get sts,pod,pvc,pv -n sandbox` and `kubectl describe pvc data-postgres-0 -n sandbox` | The chain StatefulSet → pod → PVC → PV, the event `ProvisioningSucceeded` |
| 2 | `kubectl exec -n sandbox postgres-0 -- psql -U orders -c "select status, count(*) from orders group by 1"` | The data directly in the database |
| 3 | `nslookup` for `postgres` and `postgres-0.postgres-headless` from a temporary pod (image `busybox`, needs a securityContext for `restricted`) | A regular Service — a ClusterIP; the headless one — straight to the pod's IP |
| 4 | `docker exec sre-ai-worker ls /var/local-path-provisioner` (the node name — from `kubectl get pod postgres-0 -o wide`) | The folders of all PVs on this node |
| 5 | `docker stop <the node with postgres-0>` and wait ~6 minutes | The pod hangs in `Terminating`/`Unknown`, and the StatefulSet **will not create a replacement**: it guarantees "no more than one `postgres-0`", and cannot know whether the old one is alive. After `kubectl delete pod postgres-0 --force` the new pod will be `Pending` with `volume node affinity conflict` — the volume is physically on the dead node. Restore: `docker start` |
| 6 | Copy the data: `kubectl exec -n sandbox postgres-0 -- pg_dump -U orders orders > .local/orders.sql` | The simplest backup; then delete the PVC and restore via `psql` |
| 7 | `kubectl patch pvc data-postgres-0 -n sandbox -p '{"spec":{"resources":{"requests":{"storage":"2Gi"}}}}'` | A refusal: `standard` has no `allowVolumeExpansion` — the volume size must be planned too |
| 8 | Add a retry for `NpgsqlException { IsTransient: true }` on reads to orders-api and repeat the database restart | The first requests after the restart no longer fail |
| 9 | (Advanced) Install the CloudNativePG operator and a `Cluster` with 3 instances; delete the primary pod | An automatic failover to a replica — which a single StatefulSet does not have |

## Debugging cheat sheet

| Symptom | Where to look | Common cause |
|---|---|---|
| PVC is `Pending` | `kubectl describe pvc` | No StorageClass / provisioner; with `WaitForFirstConsumer` the PVC waits until the pod is scheduled |
| Pod `Pending`: `volume node affinity conflict` | `kubectl describe pod` | The node with the local PV is unavailable |
| PVC "hangs" in `Terminating` | `kubectl get pvc -o yaml` → finalizers | A pod still uses it (`pvc-protection`) |
| postgres: `could not create directory … Permission denied` | `kubectl logs postgres-0` | A wrong uid/fsGroup, or the volume is mounted in the wrong place |
| `password authentication failed` | the postgres logs | The password in the Secret was changed after initdb — the database remembers the old one |
| The application returns 503, but `/health/db` is green | the application logs (`42P01`) | The schema was not created / the database was swapped |
| The first requests after a database restart fail | the application logs (`57P01`) | Dead connections in the pool, no retry |
