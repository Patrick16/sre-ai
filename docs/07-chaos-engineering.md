# 07. Chaos engineering

## Что это и зачем

Chaos engineering — **эксперименты** над системой, чтобы убедиться, что она переживает сбои
так, как мы думаем. Не «ломать ради ломания», а проверять гипотезы. В этом проекте у хаоса
две роли:

1. проверить устойчивость самой инфраструктуры (рестарты, probes, реплики, mesh retries);
2. быть **полигоном для агента**: контролируемо создавать проблемы и проверять, правильно
   ли агент их диагностирует и чинит.

## Метод (по шагам)

1. **Steady state** — опишите «норму» в метриках: error rate < 1%, p99 < 300 мс, все поды Ready.
2. **Гипотеза** — «если убить один под orders-api, error rate не превысит 1%, т.к. реплик 3».
3. **Blast radius** — ограничьте масштаб: один namespace, один под, ограниченное время.
4. **Эксперимент** — внедрить сбой.
5. **Наблюдение** — дашборды, алерты, поведение агента.
6. **Вывод** — гипотеза подтвердилась? Если нет — это найденная слабость, её чиним.
7. **Откат** — эксперимент должен прекращаться автоматически (duration) и вручную.

## Инструменты

### Chaos Mesh (основной)
k8s-native: эксперименты описываются CRD, ставится Helm-чартом в namespace `chaos`.

| Тип | Что делает | Что ожидаем увидеть |
|---|---|---|
| `PodChaos` pod-kill | Убивает под | Пересоздание Deployment'ом, кратковременные ошибки |
| `PodChaos` container-kill | Убивает контейнер | Рестарт, рост `restarts_total` |
| `NetworkChaos` delay/loss | Задержка/потери пакетов | Рост latency, срабатывание SLO-алерта, retries mesh |
| `StressChaos` | Нагрузка на CPU/память | Троттлинг, OOMKilled при превышении limits |
| `HTTPChaos` | Ошибки/задержки на уровне HTTP | Рост 5xx |
| `Schedule` | Эксперимент по расписанию | Регулярная «проверка» агента |

Манифесты экспериментов храним в `infra/chaos/` и всегда ограничиваем селектором
`namespaces: [sandbox]`.

### Свои инструменты на .NET (учебные)
Чтобы понимать, как хаос работает «изнутри», в проекте будет простая утилита/сервис на .NET:
- убить случайный под по label selector через k8s API (по сути маленький Chaos Monkey);
- переключить «режим неисправности» сервиса через ConfigMap/HTTP-эндпоинт.

### Встроенные режимы неисправности в sandbox-сервисах
Самый управляемый вид хаоса — баги «по флагу»:
- `latency`: добавлять N мс к ответам;
- `error-rate`: возвращать 500 в X% запросов;
- `memory-leak`: копить память до OOMKilled;
- `crash-on-start`: падать при старте (CrashLoopBackOff);
- `bad-config`: «сломанная» версия образа для проверки rollback.

## Сценарии для агента (будущие evals)

| # | Сбой | Ожидаемый вывод агента | Ожидаемое действие |
|---|---|---|---|
| 1 | pod-kill одного пода из 3 | Самовосстановилось, вмешательство не нужно | Нет |
| 2 | memory-leak в orders-api | OOMKilled, растёт память | restart (временно) + рекомендация поправить limits/код |
| 3 | Выкатка версии с crash-on-start | CrashLoopBackOff после rollout | rollback (approve) |
| 4 | Network delay к postgres | Latency выросла из-за БД, а не orders-api | Нет действия, эскалация с точной причиной |
| 5 | error-rate 30% в worker | Ошибки в логах worker | restart, проверка эффекта, при неудаче — эскалация |
| 6 | Высокая нагрузка (load test) | Saturation CPU | scale в пределах лимита |

Для каждого сценария фиксируем: нашёл ли причину, правильное ли действие, сколько шагов/токенов/времени.

## Нагрузка

Для реалистичных метрик нужен фоновый трафик: простой генератор нагрузки (k6, или свой
.NET-клиент, или CronJob с curl) в `scripts/` или как Deployment в `sandbox`.

## Правила безопасности

- хаос **только** в namespace `sandbox`;
- у каждого эксперимента есть `duration`;
- перед экспериментом — steady state зелёный; иначе результат непонятен;
- никогда не запускать хаос против `monitoring` в рамках сценариев для агента —
  агент должен видеть, что происходит.
